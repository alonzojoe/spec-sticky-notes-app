# P14 · A place for the things that are not notes — Plan

A groundwork step and six task groups. Scope and rationale live in
[requirements.md](./requirements.md); the pass/fail gate lives in [validation.md](./validation.md).

Test-first where a test is possible. Groups end with `npm run build && npm run lint && npm test`.
Commits are split by concern — `docs`, `feat`, `refactor`, `test`.

**Ordering note.** Group 4b was added mid-phase and is numbered rather than renumbering what
follows it — the same courtesy `roadmap.md` extends to itself. The amendments are group 1 and land before any code, so rejecting the claim on
the `SidebarFooter` kills the phase while the cost is two files. Group 2 builds the destination and
leaves it deliberately empty — a route, a page and the row that reaches it, with nothing on the page
— so that the two controls arrive into a place that already works rather than inventing the place
and the control in one diff. Group 3 moves the rename, which is the half of this phase that *removes*
code. Group 4 is the reset, which is the half that adds it. Group 5 is coverage; group 6 is the rest
of the documents.

## Constraints to confirm before writing code

*Proven in the repo today:*

- **The `_board` group already holds three routes** — `/`, `/notes`, `/pinned`, `/linked` — each a
  file under `routes/_board/` rendering a page from `pages/`. A fourth is a file, a page and an
  `index.ts`, and `routeTree.gen.ts` is written by the plugin.
- **`AppShell` mounts dialogs beside the sidebar** and already owns `creating` and `searching`. The
  reset confirmation does *not* join them — it belongs to the page that raises it (below).
- **`alert-dialog.tsx` is installed** (P9) and `delete_note_dialog.tsx` is the pattern: `Cancel`
  holding `autoFocus`, a `variant="destructive"` action that names the act.
- **`useLocalStorage` keeps two instances of one key in step within a tab**, verified in P13's
  groundwork. `use_reset.ts` opens a second instance on `SIDEBAR_KEY`, which is the same bet.
- **`sectionAt` falls back to the first row for an unmatched path.** `/settings` is unmatched, so
  the sidebar would draw `Notes` as active while the board is not on screen. Group 2 has to handle
  this and it is the one non-obvious thing in the group.

*To verify in group 0:*

- **The suite is green on `main`.** P13's baseline was red and its plan had to repair it first.
  #17 and #18 are merged; record the real numbers and treat them as the floor.
- **`SidebarFooter` exists in the generated `sidebar.tsx` and collapses with the rail** without an
  edit to that file, the way `SidebarHeader` does for the two rows already in it.
- **A route added under `_board/settings/` regenerates `routeTree.gen.ts` on `npm run dev`**, and
  the committed tree is what `npm run build` type-checks against. If the plugin does not run in the
  build, the file is generated by a dev run and committed in the same group.
- **`Settings` is exported by the installed `lucide-react`.** It is, in every version this project
  has had; confirm rather than assume, because a missing glyph is a build failure in the last group
  to be able to explain it.

## 2. The place, before anything is in it — `feat`

2.1 `src/pages/settings_page/settings_page.tsx` — the page, the heading, and nothing else yet.
    `bg-background`, a `max-w-xl` column, `overflow-y-auto` because the shell's outlet is
    `overflow-hidden` (**D6**). `index.ts` beside it, one line, P11's convention.

2.2 `src/app/routes/_board/settings/index.tsx` — `createFileRoute('/_board/settings/')`. Run the
    dev server once so the plugin regenerates `routeTree.gen.ts`; commit the generated file in this
    group.

2.3 **`app_sidebar.tsx` gains a `SidebarFooter`** holding one `SidebarMenuButton asChild` wrapping a
    `Link to="/settings"`, with the `Settings` glyph, the label, the `DESTINATION` class and a
    tooltip. No badge (**D2**).

2.4 **Fix what `sectionAt` would otherwise say.** It falls back to `SECTIONS[0]` for any unmatched
    path, so on `/settings` the sidebar would light `Notes` while the board is not on screen. The
    destinations' `isActive` becomes a question about the path rather than about the fallback row —
    `active.path === pathname` before a row can claim to be current — so exactly one row in this
    sidebar is ever active, and on `/settings` it is the footer's.

    **The registry is not touched.** `sectionAt`'s fallback is correct for what it is for — deciding
    which notes `/` draws — and the sidebar's question is a different one. Changing the registry to
    answer both is how a section list learns about a page that has no notes.

2.5 Gate. The page is reachable, empty, and the footer row is the only active row when you are on
    it.

2.6 Commit: `feat(settings): a route, a page and the row that reaches it`.
